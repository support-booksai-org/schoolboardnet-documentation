# Writing Style

**Status:** Draft  
**Version:** 1.0.0-draft  
**Owner:** schoolboardnet, LLC  

## Purpose

This guide defines the writing style for the schoolboard.net Documentation Suite. It applies to manuals, Knowledge Base articles, AI training articles, quick cards, release notes, and internal support documentation.

## Voice and Tone

schoolboard.net documentation should be:

- Clear
- Helpful
- Professional
- Calm
- Accessible
- Practical
- Respectful of non-technical users

Write as a trusted guide. Avoid marketing language in procedural documentation. Explain why a workflow matters when it helps users make better decisions.

## Reading Level

Use plain language suitable for administrators, board clerks, administrative assistants, and district staff. When possible, write so a middle-school student could follow the steps.

## Sentence Style

Use short sentences. Prefer active voice.

Recommended:

> Select **Save** to store the agenda item.

Avoid:

> The agenda item may be stored by selecting the Save button.

## Procedure Style

Use numbered steps for tasks that must be completed in order.

Example:

1. Sign in to schoolboard.net.
2. Open the administrator dashboard.
3. Select **Content**.
4. Select **Add content**.
5. Select **Accordion Agenda**.

## Button and Field Names

Use bold text for interface labels, buttons, tabs, and fields.

Examples:

- Select **Save**.
- Open the **Groups** page.
- Enter the title in the **Title** field.

## Links

Use descriptive links.

Recommended:

> See [Reset a User Password](../03-administrator-training-guide/07-reset-password.md).

Avoid:

> Click here.

## Accessibility Language

When explaining accessibility, focus on practical outcomes.

Recommended:

> Proper headings help screen reader users move through a document quickly.

Avoid:

> Headings are required for compliance.

## AI Language

AI-assisted conversion should be described as a review-supported workflow. Never imply that AI output should be published without review.

Recommended:

> Review AI-generated HTML before publishing it to confirm that headings, links, lists, tables, and accessibility labels are correct.

Avoid:

> AI conversion automatically creates compliant HTML.

## Preferred Terms

Use official terminology from `terminology.md`.

## Chapter Structure

Every chapter should follow `templates/chapter-template.md` unless there is a documented reason to vary the structure.

## Knowledge Base Structure

Every Knowledge Base article should follow `templates/kb-article-template.md`.
